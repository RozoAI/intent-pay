# Native-token payment options: pre-fix source audit

**Historical baseline:** findings below describe code before implementation work on [native-token-payments-plan.md](./native-token-payments-plan.md). Current worktree now passes merchant `appId` in deposit requests, recognizes opted-in EVM native sources, normalizes native SOL/XLM aliases, and emits the canonical Solana System Program ID in the proxy. Use current source/tests for implemented behavior. Local diagnosis using the proxy's configured Axios endpoint returned HTTP 200 with 18 supported rows for `rozoBridgeStellar` but no opt-in ETH/BNB/POL/SOL rows; unfiltered wallet scan returned five native balances, which merchant filter removed. Earlier standalone Python requests returned HTTP 403. Backend integration owner clarified outbound `getFee`/`createPayment` source identities: EVM native = zero address, SOL = `"native"` (not the proxy/UI sentinels). The shared request builder now maps these and includes both source and destination token addresses. Backend checkout acceptance and funded settlement remain unverified. No request sent with supplied payer address. Paths below are repo-relative unless prefixed `api-proxy-only/` (sibling checkout).

## Answer for supplied batch

`getWalletPaymentOptions` is **EVM-wallet balances only**, not a catalog of all source assets. It independently queries supported EVM networks, including native balances, but returns only recognized **nonzero holdings with usable USD prices**, then **removes native ETH/BNB/POL unless merchant `appId` is opted in**. `destChainId:8453` specifies destination, not source network. `preferredTokens` chain/address objects are ignored by this proxy handler; `preferredTokenAddress` addresses only affect ordering, not eligibility. Therefore stablecoin-only preferences in raw proxy request **do not explain missing ETH**. Absence of a merchant opt-in, zero native balance on queried chains, failed chain RPC, or missing price listing can; static code cannot establish which affected supplied wallet. See `api-proxy-only/src/server.ts:628-653`, `api-proxy-only/src/lib/evm.ts:128-150,179-293,342-412`, `api-proxy-only/src/lib/nativeAllowlist.ts:1-16,91-116,139-169`.

`getDepositAddressOptions` is a **static catalog** (no payer balance required), built with ETH on Ethereum/Base/Arbitrum, POL on Polygon, BNB on BSC, SOL on Solana and XLM on Stellar. But batch dispatcher filters opt-in native assets using **that endpoint's own** `input[1].appId`, not `input[0].appId`; when omitted, lookup returns empty allowlist and removes EVM/SOL native entries. XLM deliberately bypasses merchant-native allowlist and remains visible. This exactly explains supplied catalog's stablecoins + XLM. See `api-proxy-only/src/lib/deposit.ts:81-121`, `api-proxy-only/src/server.ts:614-625`, `api-proxy-only/src/lib/nativeAllowlist.ts:32-73,119-130,139-160`; unit assertions `api-proxy-only/src/__tests__/unit/nativeAllowlist.test.ts:62-91,132-139`.

Raw proxy response versus widget display **differ**: `intent-pay/packages/connectkit/src/hooks/useWalletPaymentOptions.ts:94-106` sends both preference fields, but `:113-149` *hard-filters* options to `supportedTokens` and the configured `(chainId,token)` `preferredTokens` list. Deposit hook also hard-filters preference pairs (`packages/connectkit/src/hooks/useDepositAddressOptions.ts:118-145`). Thus stablecoin-only `preferredTokens` does hide native assets **in SDK UI**, even though it does not hide them from this proxy's raw response. Default symbol converter claims to include native tokens but iterates `supportedTokens`, which currently includes SOL/XLM but **no EVM native coins** (`packages/connectkit/src/utils/token.ts:7-75`; `packages/pay-common/src/token.ts:961-973`). Even if proxy returns ETH/BNB/POL, current SDK EVM `isSupported` removes them; adding EVM native tokens to caller's preferred list alone does not fix that registry gate. Native EVM tokens exist in separate `tokensByChainAndType` registry, but not `supportedTokens`/`getKnownToken` (`packages/pay-common/src/token.ts:991-1027,1035-1062,1190-1195`). This is a concrete current widget limitation, not a backend assertion.

### Request shapes and practical use

For a **raw proxy** batch, send tRPC-style `GET /getWalletPaymentOptions,getDepositAddressOptions?batch=1&input=<URL-encoded JSON>`, with separate numeric keys. Example (use your own payer, opted-in merchant, destination):

```json
{
  "0": {
    "payerAddress": "<EVM wallet>",
    "destChainId": 8453,
    "usdRequired": 0.023,
    "appId": "<merchant appId with native ETH enabled>",
    "type": "exactIn"
  },
  "1": {
    "appId": "<same merchant appId>",
    "usdRequired": 0.023,
    "mode": "<your deposit mode>"
  }
}
```

This proxy ignores `usdRequired`/`mode` for catalog generation; second `appId` matters for filtering. Request `0` requires `payerAddress`, `destChainId`, numeric `usdRequired` if present; `type` defaults `exactIn` (`api-proxy-only/src/server.ts:628-655`). `preferredTokenAddress?: string[]` is an **address-only ranking hint** on EVM, not a native-enable switch (`api-proxy-only/src/lib/evm.ts:400-412`). Prefer omit it for diagnosis. `preferredTokens: [{chain:8453,address:"..."}]` originates in SDK but is **not read** by local proxy (`packages/connectkit/src/hooks/useWalletPaymentOptions.ts:86-105`; `api-proxy-only/src/lib/evm.ts:114-125`). To rank Base ETH first when returned, use native EVM sentinel `0xEeeeeEeeeEeEeeEeEeEeeEEEeeeeEeeeeeeeEEeE` under `preferredTokenAddress`; this is not sufficient for opt-in, nonzero balance or UI filtering (`api-proxy-only/src/lib/token.ts:78-81,164-177`). Do not substitute destination zero address here; source sentinel differs from destination native-address convention (`packages/connectkit/src/components/RozoPayButton/types.ts:18-27`).

For **SOL wallet options**, use separate `getSolanaPaymentOptions` with `{ "pubKey":"<Solana public key>", "usdRequired":0.023, "appId":"<opted-in merchant>" }`; source SOL opt-in asset key is `SOL@900` even though local proxy returns chain `501`. For **XLM wallet options**, use separate `getStellarPaymentOptions` with `{ "stellarAddress":"<Stellar G... account>", "usdRequired":0.023, "appId":"<merchant>" }`; XLM is not subject to same merchant-native allowlist, but requires Horizon account/native balance and a native price. Batch dispatcher supports both routes (`api-proxy-only/src/server.ts:656-705`); balance/price paths `api-proxy-only/src/lib/solana.ts:93-183`, `api-proxy-only/src/lib/stellar.ts:55-178`; mapping `api-proxy-only/src/lib/nativeAllowlist.ts:32-47`. Do not put SOL/XLM addresses in EVM `payerAddress` endpoint.

Configure merchant's native **source-chain** assets in upstream Intents API's `merchant_native_tokens` opt-in; proxy reads `GET <intents>/payment-api/payments/supported?appId=...`, accepts `tokenSymbol`/`chainId` pairs and fails closed if missing appId, lookup error, or absent pair. Lookup URL defaults to `https://intentapiv4.rozo.ai/functions/v1/payment-api/payments/supported`, overridable by `NATIVE_ALLOWLIST_URL`; timeout 3s; success cache 60s, failure cache 10s (`api-proxy-only/src/lib/nativeAllowlist.ts:1-29,76-136`). EVM RPC needs `ALCHEMY_API_KEY` and enabled networks (`api-proxy-only/src/lib/evm.ts:93-99,157-334`; `api-proxy-only/CLAUDE.md:86-98`). Native prices use `TOKEN_PRICES_UPSTREAM_URL` or default Intents `/token-prices`, 15s cache, fall back to hardcoded prices on transport error but **not** per-symbol unlisted price (`api-proxy-only/src/lib/price.ts:3-78`). Backend-specific merchant provisioning/quote support is described by proxy comments but **not verifiable** without the separate `rozo-intents-api` repo or live supported/quote response. Confirm merchant configuration there before promising payment execution.

SDK currently calls deposit catalog without `appId` (`packages/connectkit/src/hooks/useDepositAddressOptions.ts:93-110`), so **widget deposit native EVM/SOL always fail-closed against this proxy**, even with an opted-in merchant, unless request path is changed. A direct raw request with `input[1].appId` can reveal catalog entries, but does not fix widget. SDK also filters catalog by `preferredTokens` and has static stablecoin-only fallback on query error (`packages/connectkit/src/hooks/useDepositAddressOptions.ts:22-75,103-145`).

Important second SOL compatibility issue: proxy's SOL `token` sentinel is `11111111111111111111111111111112`, while intent-common uses `11111111111111111111111111111111` (`api-proxy-only/src/lib/token.ts:277-288`; `packages/pay-common/src/token.ts:704-711`). SDK token recognition and preferred filtering compare chain+address; `isNativeToken` only recognizes the latter (`packages/pay-common/src/token.ts:961-973,1265-1273`; `packages/connectkit/src/hooks/useSolanaPaymentOptions.ts:100-139`). Thus raw SOL option is possible, but **this SDK cannot safely be assumed to display/transfer it as native** without normalizing sentinels across services. Note local proxy Solana chainId 501 versus public Intents chainId 900 (`api-proxy-only/src/lib/deposit.ts:75-91`; `api-proxy-only/src/lib/nativeAllowlist.ts:32-47`).

### End-to-end path and limits

```text
RozoPayButton params/appId/preferredTokens
  → SDK hooks → proxy EVM/Solana/Stellar balance RPC + native USD price
  → proxy merchant-supported allowlist (ETH/BNB/POL/SOL; XLM exempt)
  → SDK supportedTokens & preferredTokens filters → select source
  → create/checkout upstream Intents API with preferredChain,
    preferredTokenAddress, preferredAmountUnits
  → SDK native EVM value transfer / Solana SystemProgram.transfer /
    Stellar Asset.native() payment to quoted receiving address
```

Source quote path: `packages/connectkit/src/payment/createPaymentPayload.ts:176-210,261-273` preserves wallet option source units as `preferredAmountUnits` and selects source chain/token; native EVM transaction uses quoted amount via `sendTransactionAsync({to,value})` (`packages/connectkit/src/hooks/usePaymentState.ts:865-910,974-1001`), SOL uses `SystemProgram.transfer` (`:1225-1249`), XLM uses `Asset.native()` (`:1377-1408`). These execution branches establish code paths, **not** proof production backend accepts a particular merchant/source/destination combination. Destination `toChain:8453`/`toToken`/`toAddress` remain separate from source; do not treat `usdRequired` or proxy's initial `required.amount` as authoritative execution quote (`packages/connectkit/src/payment/createPaymentPayload.ts:151-183,261-273,323-349`).
